# 1. Purpose

The backend doesn't know or care whether its caller is this Svelte SPA or a third-party integration — every rule that matters is enforced server-side. This document is about the other half: how the SPA stays fast, how a module contributes a page without touching core, and where the frontend's permission checks fit given that they are UX, never security (06 §15).

## 1.1 Technology baseline

| Area | Choice |
|---|---|
| Framework | **Svelte 5** (runes), plain SPA — not SvelteKit |
| Build | Vite, TypeScript in `strict` mode |
| Workspaces | npm workspaces: `apps/web`, `packages/ts-sdk`, `packages/ui`, `modules/*/frontend` |
| Node | current LTS (24) |
| Unit/component tests | Vitest |
| E2E | Playwright |
| Router, UI kit, i18n library | chosen by an ADR in the frontend-foundation milestone against the criteria in §4 and §10 |

# 3. Svelte Conventions

Svelte 5 runes (`$state`, `$derived`, `$effect`) for component-local and page-level state. A small number of classic stores remain justified for genuinely global, cross-component singletons that need to be imported and subscribed to from arbitrary depth without prop-drilling — the WebSocket connection state and the current `Identity` are the two canonical cases (`core/websocket`, `core/auth`). Everything else defaults to runes.

Plain Vite + Svelte SPA, not SvelteKit — there is no server-rendering requirement here (the platform's own security model is a same-origin cookie + CSRF pair talking to the Go API, 05 §2), and SvelteKit's file-based routing/SSR machinery would be solving a problem this platform doesn't have. (SvelteKit with `adapter-static` in SPA mode remains a legitimate alternative if the routing ADR in §4 finds it preferable; the rest of this document is unaffected.)

**Same-origin.** The SPA is served from the same origin as the API. In development the Vite dev server **proxies** `/api` and `/ws` to the Go API (`vite.config.ts`); in production a reverse proxy serves the static bundle and forwards `/api` and `/ws` (15 §6). The frontend therefore uses **relative URLs only** and never contains an API host — no CORS configuration is needed or allowed.

# 4. Routing

A lightweight client-side router resolves two kinds of routes. The specific package is decided by an ADR against these criteria: supports Svelte 5, history-mode URLs, route guards / `beforeEnter`, lazy-loaded route components, nested layouts, and is actively maintained. (Candidates to evaluate include `svelte-routing`-family libraries and a thin custom wrapper over the History API; SvelteKit SPA mode is the alternative noted in §3.)

```text
Core routes         — registered directly in apps/web/src/routes/
Module routes        — registered by each module's manifest (07 §4: frontend.routes[]),
                        collected into the router at app startup from modules_gen.ts by
                        core/module's registry (§5)
```

Every route — core or module — passes through the same route guard, which checks authentication (redirect to login if absent) and then the route's declared `requires_permission` (redirect to a 403 page, not just hide navigation, if present but denied) before rendering.

# 5. The Module Registry (`core/module`)

## 5.1 Build-time inclusion, run-time filtering

A business module's frontend code ships inside the built application bundle for every organization (registered through the generated `modules_gen.ts`) — Vite doesn't dynamically fetch a module's Svelte components from a server at runtime for v1.0. What varies **per organization, per user, at runtime** is which of those already-bundled routes and menu entries are actually reachable:

```text
route/menu shown  ⟺  module is enabled for the caller's active organization (07 §3)
                     AND caller's effective permissions include the route's requires_permission
```

This is a deliberate simplification: it avoids building a dynamic-import/module-federation pipeline before there's a second real module to prove it against, at the cost of every organization downloading every installed module's frontend code even if disabled for them. Per-module code-splitting via Vite's `import()` (so a disabled module's bundle is never even fetched) is the natural next step once bundle size becomes a real complaint (20 §3). The route components are already declared as lazy (`() => import(...)`) so that step needs no contract change.

## 5.2 Registry shape

```ts
interface ModuleFrontendManifest {
  code: string;
  routes: { path: string; component: () => Promise<Component>; requiresPermission?: string }[];
  menu: { label: string; icon: string; route: string; requiresPermission?: string }[];
  i18n?: Record<string, () => Promise<Record<string, string>>>;   // locale → catalog loader
}
```

`core/module` merges every registered module's manifest with the live "which modules are enabled for my organization" response from the API (07 §14) to produce the actual set of visible routes and menu items for the current session.

# 6. Permission Gating (`core/permission`)

```ts
function can(permission: string): boolean
```

Backed by the effective-permission set the API returns once, at login and on session/scope refresh (06 §5.2 computed the same way server-side; the frontend simply receives the resulting list, it never recomputes the logic itself). `PermissionGate.svelte` (07 §11) wraps this into a component so a module author writes:

```svelte
<PermissionGate permission="invoice.approve">
  <button onclick={approve}>Approve</button>
</PermissionGate>
```

instead of a `{#if}` re-implemented per page. This exists purely for consistent UX — hiding a button a user can't use — and never as the actual security boundary; every one of these actions is re-checked server-side regardless (06 §15, rule 2).

**Limits of `can()`.** The session-level set contains only permissions that do not depend on a specific resource: `resource`- and `own`-scoped grants, and policies that look at resource state, cannot be known in advance (06 §5.2, §6). For per-record buttons (approve *this* invoice, edit *this* post) a detail response carries `meta.allowed_actions` computed by the server for that caller and that record (08 §3.1), and a component uses it instead of `can()`. Both are UX only.

Field-level permissions (06 §7) need no frontend equivalent to enforce — a restricted field is simply **absent** from the API response the frontend receives, so a list/detail component that renders "whatever fields came back" is correct by construction and never needs its own permission logic per field.

# 7. API Client (`core/api`)

```text
packages/ts-sdk/     generated from the OpenAPI document (08 §9's swag output), regenerated
                      by `make generate` and checked in CI for drift (19 §3)
apps/web/src/core/api/   a thin wrapper around ts-sdk that adds:
                      - the X-Active-Group-ID header (from core/auth's current-group state)
                      - the X-CSRF-Token header (fetched once per session, refreshed on rotation)
                      - X-Request-ID generation
                      - Idempotency-Key generation for the endpoints that require it (08 §6)
                      - centralized handling of the {error: {code, ...}} envelope,
                        translating `code` through the i18n catalog (§10) before it
                        reaches a component
                      - 401 handling: clear session state and redirect to login
```

A component never calls `fetch` directly and never reaches into `ts-sdk` unwrapped — everything goes through `core/api` so the cross-cutting headers and error handling can't be forgotten on any single call site. All URLs are relative (§3).

# 8. WebSocket Client (`core/websocket`)

```text
connect() on login to the same-origin /ws endpoint, using the same session cookie (09 §2)
     │
     ▼
on message → dispatch by frame `type` (09 §2.4, §5) to the
             relevant store (notifications, inbox, chat, presence)
     │
     ▼
on disconnect → exponential backoff (with jitter) reconnect, sending `last_seen`
                (09 §2.3); on `resync_required` refetch the affected state over REST
```

Duplicate-safe by contract: since delivery is at-least-once (09 §2.3), every store that consumes a WebSocket event keys its state by the event's resource `id` and treats a repeat as a no-op update, never an append. A close code 4401 (session revoked) sends the user to the login page rather than retrying.

# 9. Active Group Switching

The group-switcher component (part of `layouts/`, visible whenever the current user belongs to more than one group) updates `core/auth`'s current-group state, which `core/api` then attaches as `X-Active-Group-ID` on every subsequent request (06 §4.2). Switching groups triggers a re-fetch of the effective-permission set and the visible module/menu set (§5, §6) — a Finance-group view and an Events-group view of the same logged-in session can look meaningfully different, and the switch needs to update both what's shown and what's actually allowed in the same moment, not one after the other. Switching *organization* calls `switch-organization`, receives a new session, and reloads application state from scratch.

# 10. Internationalization

Given the stated goal of an internationally usable platform, i18n is core infrastructure, not a module concern:

```text
apps/web/src/core/i18n/
├── en-US.json
├── id-ID.json
└── ...
```

- UI strings are translation keys, resolved from the user's `locale` (04 §6 — `users.locale`), never hardcoded English in a component. The i18n library is chosen by the foundation ADR; requirements are ICU-style plurals/interpolation, lazy-loaded catalogs, and Svelte 5 compatibility.
- API error `code` and notification `type` (08 §8) are resolved through the **same** catalog, under an `errors.*` / `notifications.*` namespace, with `data` as parameters, so a Finance module ships its own translation entries (`notifications.finance.invoice.approved`) alongside core's without either needing to know about the other's keys.
- A module's manifest may ship its own translation file, merged into the catalog at module-registration time — the same "modules extend, core doesn't need to know" pattern as everywhere else in this platform.
- Dates, numbers, and currency are formatted via `Intl` against the user's `locale` and the organization's `default_timezone`/`default_locale` (04 §5) as the fallback for values that aren't inherently user-specific.

# 11. Testing Conventions

```text
Component        — unit tests for logic-bearing components (forms, PermissionGate, the
                    module registry's merge logic, core/api header + envelope handling),
                    not for pure presentational markup
E2E                — a real browser (Playwright) driving the full login → action → verify
                    flow against a real backend, for the handful of flows where an
                    integration bug would be expensive to ship (login, invitation accept,
                    group admin workflow, group switching, chat between two users)
Permission gating   — a dedicated test category: for a given fixture permission set,
                    assert the correct buttons/fields are absent from the RENDERED output,
                    not just that a `can()` call returned false somewhere
```

Full detail lives in 18-testing-strategy.md; this section only establishes that "the button is hidden" and "the server actually denies it" are two different test suites, and neither one substitutes for the other.

# 12. Critical Rules

```text
1.  No authentication token is ever stored in localStorage or sessionStorage
    — the session lives only in the HttpOnly cookie (05 §2, §22).
2.  Every API call goes through core/api — never a raw fetch, never
    ts-sdk unwrapped — so cross-cutting headers can't be silently skipped.
3.  A permission check on the frontend controls visibility only. It is never
    treated as proof an action is allowed, and it is never the last check
    performed before a mutating call is sent.
4.  A restricted field's absence is handled by rendering only what's present
    — a component must never assume a field exists and crash or fall back
    to a guessed default when the API correctly omits it.
5.  User-facing strings are translation keys, not literals, from the first
    component written — retrofitting i18n later is far more expensive than
    starting with it.
6.  The SPA uses relative URLs and talks only to its own origin; no API host,
    no CORS workaround, no token in a URL or query string.
7.  Untrusted content (chat messages, user-supplied names, notification data) is rendered as text,
    never injected as HTML; any rich rendering goes through a sanitizer and is reviewed.
```
