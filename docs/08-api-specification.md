# 1. Purpose

Without one place stating the shared rules — pagination, errors, headers, versioning — every module author would invent their own, and a third-party module's API would feel like a different product from core's. This document is that shared contract, plus the endpoint groups (Organizations, Groups, Users, Profile, Invitations) that didn't belong to any single domain document.

The **generated OpenAPI document is the actual source of truth for exact field-level shapes** (§9) — this document is the human-readable conventions layer above it.

---

# 2. General Conventions

```text
Base path:        /api/v1
Content type:     application/json (request and response bodies)
Field naming:     snake_case
Timestamps:       ISO 8601, UTC, e.g. "2026-09-13T08:21:00Z"
IDs:              UUIDv7 string
Origin:           same-origin with the SPA (no CORS); see 15 §6
```

The API is served **same-origin** with the SPA: in development through the Vite proxy, in production through the reverse proxy. CORS is therefore not enabled; a deployment that needs a cross-origin client (for example a future mobile app) gets a separate, explicitly configured CORS policy, not a wildcard.

## 2.1 Versioning

`/api/v1` is a breaking-change boundary, not a per-endpoint one. A breaking change to any single endpoint means introducing `/api/v2` for the whole surface, with v1 kept running in parallel until every known client has migrated. Additive changes (a new optional field, a new endpoint) never require a version bump.

## 2.2 Standard headers

| Header | Direction | Purpose |
|---|---|---|
| `Cookie: platform_session=...` | request | Authentication (05 §2) |
| `X-CSRF-Token` | request | Required on all mutating requests (05 §8) |
| `X-Active-Group-ID` | request | Group scope hint for ambiguous actions (06 §4.2) |
| `X-Request-ID` | request/response | Correlates a request across services and logs; generated by the client if absent (or by the server if invalid), echoed back either way |
| `Idempotency-Key` | request | Required on the mutating endpoints listed in §6 |
| `X-RateLimit-Limit` / `-Remaining` / `-Reset` | response | Rate-limit visibility (§7) |
| `Retry-After` | response | On `429` and `503` |

## 2.3 Request limits

Request bodies are limited (default 1 MiB for JSON endpoints; uploads have their own per-endpoint limit, 09 §8.2). An oversized body returns `413 payload_too_large`; a wrong `Content-Type` returns `415 unsupported_media_type`. Unknown JSON fields are rejected (`validation_failed`) to prevent silent over-posting.

## 2.4 Optimistic concurrency

Resources that are edited concurrently (settings, module configuration, conversations, selected business records) carry a `version` integer. An update sends the `version` it read; a stale one returns `409 version_conflict` (03 §48) instead of silently overwriting another user's change.

# 3. Response Envelope

## 3.1 Success

```json
{
  "data": { "...": "..." },
  "meta": { "...": "optional — pagination, counts, allowed_actions, etc." }
}
```

A single resource returns `data` as an object; a collection returns `data` as an array plus `meta.pagination` (§4). A detail response may include `meta.allowed_actions` — the actions *this caller* may perform on *this resource* (for example `["update","approve"]`), computed server-side. The frontend uses it to render per-resource buttons, because resource- and own-scoped permissions cannot be known from the session-level permission list (11 §6). It is UX only; every action is re-authorized when performed.

## 3.2 Error

Identical shape everywhere in the platform — every error code referenced across 05, 06, 07, 09, and 13 renders through this one envelope:

```json
{
  "error": {
    "code": "permission_denied",
    "message": "You do not have permission to perform this action.",
    "request_id": "req_01...",
    "details": { "...": "optional, machine-readable — e.g. field-level validation errors" }
  }
}
```

`message` is a **default, English fallback** for logging and for clients that don't localize — see §8. `code` is what a client should actually branch on. Unrecognized server errors always return `internal_error` with no detail; the full detail goes to the system log (10 §9).

# 4. Pagination

**Cursor-based (keyset)** for anything that can grow large and is usually read in recency order — activities, system logs, notifications, messages:

```text
GET /api/v1/activities?limit=50&cursor=eyJ...
```

```json
{
  "data": [ /* ... */ ],
  "meta": {
    "pagination": {
      "next_cursor": "eyJ...",
      "has_more": true
    }
  }
}
```

The cursor is opaque to clients and **HMAC-signed** by the server: it encodes the last row's `(created_at, id)`, the sort direction, and a hash of the active filters. A tampered cursor, or one reused with different filters, returns `400 validation_failed` — never a silently wrong page. Ordering is always by `(created_at, id)`; `id` alone is not enough because UUIDv7 values generated on different instances are not strictly monotonic. `limit` has a server-side maximum (default 100).

**Offset-based** is acceptable only for small, admin-managed lists that are realistically never going to exceed a few hundred rows (roles, permissions, modules, organizations from a Super Admin's view):

```text
GET /api/v1/roles?page=1&per_page=25
```

```json
{ "data": [ /* ... */ ], "meta": { "pagination": { "page": 1, "per_page": 25, "total": 42 } } }
```

Cursor pagination is the default for any *new* module endpoint unless the resource is provably small — offset pagination on a fast-growing table degrades under real load (`OFFSET 500000` still scans and discards 500,000 rows) in a way that only shows up after a deployment has real data in it.

# 5. Filtering & Sorting

```text
GET /api/v1/activities?action=invoice.approved&resource_type=invoice&since=2026-09-01
GET /api/v1/roles?sort=-created_at
```

A leading `-` reverses sort direction. Filterable/sortable fields are an explicit allowlist per endpoint (defined in the generated OpenAPI spec, §9) — never "whatever column name happens to match," which would leak schema details and let a client filter on something like `secret_hash` by guessing.

---

# 6. Idempotency

Required, via `Idempotency-Key`, on mutating endpoints where a retried network request must not double-apply:

```text
POST /api/v1/security/password
POST /api/v1/modules/{code}/install
POST /api/v1/role-assignments
POST /api/v1/organizations/{org_id}/modules/{code}/enable
POST /api/v1/organizations/{org_id}/modules/{code}/disable
POST /api/v1/organizations/{org_id}/invitations
POST /api/v1/conversations
(and any module route declared with `Idempotent()`, 07 §5.1)
```

The server stores the result in **Redis for 24 hours** under a key scoped to the caller: `idem:{user_id}:{method}:{route}:{key}` → `{request_hash, status, headers, body}`. A retried request with the same key and the same body returns the original response without re-executing; a same key with a **different** body is `422 idempotency_key_conflict`; a duplicate that arrives while the first is still running is `409 idempotency_in_progress`. Because the key includes the user, one user can never replay another user's stored response. If Redis is unavailable, requests that *require* a key fail closed (`503 service_unavailable`) rather than executing without protection.

# 7. Rate Limiting

Every response carries the standard trio of headers (§2.2); a `429` uses the same error envelope:

```json
{ "error": { "code": "rate_limit_exceeded", "message": "Too many requests." } }
```

Sensitive endpoints (login, forgot/reset password, accept-invitation, MFA verify — 05 §12.3) have tighter, dedicated limits on top of the general per-user/per-IP limits everything else shares. Client IP is taken from `X-Forwarded-For` only when the immediate peer is in `TRUSTED_PROXIES` (10 §8); otherwise from the socket address. If Redis is unavailable, the limiter falls back to a conservative per-instance in-memory limit for sensitive endpoints rather than disabling limiting.

# 8. Localization

The frontend, not the backend, decides what language to render — which only works if the backend never hands it a hardcoded English sentence to display as-is.

- `error.code` and `error.details` are stable, machine-readable strings. `error.message` is an English fallback only — the frontend maps `code` through its own translation catalog for anything user-facing.
- The same applies to notification `type` (09 §6) — the notification's *text* is rendered client-side from a template keyed by `type` with the parameters in `data`, not sent as a pre-formatted string from the server (`title`/`body` are optional English fallbacks), so a user with `locale = id-ID` sees Indonesian without the backend needing to know Indonesian.
- `Accept-Language` is accepted for the handful of things that genuinely are rendered server-side (transactional emails sent by the worker, using the recipient's stored `locale`) but never governs the shape or field names of a JSON response.

# 9. OpenAPI Generation

**Decision: `swaggo/swag` annotations, generated from code, is the single source of truth.** (The project history includes hand-maintained YAML; it is not used.)

```go
// CreateInvoice godoc
// @Summary      Create an invoice
// @Tags         finance
// @Accept       json
// @Produce      json
// @Param        body body CreateInvoiceRequest true "Invoice payload"
// @Success      201 {object} InvoiceResponse
// @Failure      403 {object} ErrorResponse
// @Router       /api/v1/finance/invoices [post]
func (h *Handler) CreateInvoice(w http.ResponseWriter, r *http.Request) { ... }
```

Reasoning: a hand-maintained YAML file drifts from the actual implementation the moment someone changes a handler and forgets the doc — there is no way for that drift to be caught automatically. Annotations next to the code they describe, regenerated by `make generate` and checked in CI (regenerate, then `git diff --exit-code` against the committed `docs/swagger.json` and `packages/ts-sdk/` — 19 §3), close that gap structurally instead of relying on discipline. A **module** contributes to the same generated document by annotating its own handlers identically — core does not maintain a separate spec per module.

The swag v1 generator emits OpenAPI 2.0. Whether to move to swag v2 (OpenAPI 3.x) and which TypeScript generator to use (`openapi-typescript` is the default candidate) is decided by an ADR in the frontend foundation milestone; either way the committed generated output is what the TypeScript SDK is built from.

# 10. Endpoint Catalog

Grouped by domain. Behavior for each group beyond basic CRUD is defined in the document noted — this table exists so the full surface is visible in one place.

```text
GET /api/v1/system-logs               (Super Admin only)
```

## 10.6 Organizations & Invitations *(not defined elsewhere)*

```text
GET    /api/v1/organizations                  (Super Admin: all; others: their memberships)
POST   /api/v1/organizations                  (Super Admin only)
GET    /api/v1/organizations/{id}
PATCH  /api/v1/organizations/{id}
DELETE /api/v1/organizations/{id}              (soft delete → status = archived)
GET/POST/DELETE /api/v1/organizations/{id}/members

GET    /api/v1/organizations/{id}/invitations
POST   /api/v1/organizations/{id}/invitations           (Idempotency-Key required)
DELETE /api/v1/organizations/{id}/invitations/{inv_id}  (revoke)
```

Accepting an invitation is unauthenticated and lives under `/auth/accept-invitation` (05 §13.3).

## 10.7 Groups *(new)*

```text
GET/POST/PATCH/DELETE /api/v1/groups, /groups/{id}
GET/POST/DELETE        /api/v1/groups/{id}/members
POST                    /api/v1/groups/{id}/members/{user_id}/activate
```

`activate` exists as its own endpoint (rather than folded into a generic `PATCH .../members/{id}`) because it's the specific action in the group-admin workflow — a Group Admin adding a user and then explicitly activating them — and giving it a named, auditable action makes that step visible in the Activity Log as `group.member.activated` rather than an undifferentiated `member.updated`.

## 10.8 Users *(new)*

```text
GET/POST/PATCH/DELETE /api/v1/users, /users/{id}
```

`DELETE` is a soft delete (`status = deactivated`, sessions revoked, 02 §36).

## 10.9 Profile *(new — the caller acting on themselves, distinct from admin-managed Users)*

```text
GET/PATCH /api/v1/profile
```

Kept as its own endpoint rather than `PATCH /users/{me.id}` because "edit my own profile" and "an admin edits a user record" are different permissions (`profile.update` vs `user.update`) even when they touch the same row — collapsing them would force one permission to cover both, which breaks the field-permission model (06 §7): a field a user may edit on themselves (`display_name`) may not be one a Group Admin should be able to edit on them (`status`).

# 11. Consolidated Error Registry

One flat namespace, so two different domains never accidentally reuse the same code for different meanings:

```text
Auth (05)             authentication_required, invalid_credentials, account_locked,
                       account_suspended, mfa_required, invalid_mfa_code,
                       session_expired, session_revoked, csrf_failed,
                       rate_limit_exceeded, invalid_reset_token, invalid_invitation

Authorization (06)    permission_denied, invalid_scope, scope_mismatch,
                       role_not_found, permission_not_found,
                       grant_exceeds_authority, policy_evaluation_failed,
                       field_permission_denied

Modules (07)          module_not_found, module_already_installed,
                       module_dependency_missing, module_version_incompatible,
                       module_migration_failed, module_manifest_invalid,
                       module_circular_dependency, module_permission_conflict,
                       module_not_enabled

Realtime (09)         conversation_not_found, not_a_conversation_member,
                       message_too_large, invalid_message_type,
                       websocket_unauthorized, subscription_denied,
                       attachment_rejected

Audit (13)            activity_access_denied, system_log_access_denied,
                       export_scope_exceeded, invalid_date_range

General (this doc)    validation_failed, resource_not_found, internal_error,
                       version_conflict, payload_too_large, unsupported_media_type,
                       idempotency_key_conflict, idempotency_in_progress,
                       unsupported_api_version, service_unavailable
```

HTTP mapping: `validation_failed` 400 (422 for `idempotency_key_conflict`), `authentication_required` 401, `permission_denied` 403, `resource_not_found`/`module_not_enabled` 404, `version_conflict`/`idempotency_in_progress` 409, `payload_too_large` 413, `unsupported_media_type` 415, `rate_limit_exceeded` 429, `internal_error` 500, `service_unavailable` 503.

A module registering its own errors prefixes them with its module code (e.g. `finance.invoice_already_approved`) specifically so it can never collide with this registry or another module's.

# 12. Testing Requirements

```text
Envelope
  every success response matches the {data, meta?} shape
  every error response matches the {error: {code, message, request_id}} shape
  an unrecognized server error returns internal_error with no detail

Pagination
  cursor pagination returns has_more=false on the last page
  a tampered, truncated, or filter-mismatched cursor returns 400, not a 500 or a silently-wrong page
  ordering is stable for rows with equal created_at (tie-break by id)

Idempotency
  identical (key, body) retried → same response, operation not repeated
  same key, different body → idempotency_key_conflict
  concurrent duplicate → idempotency_in_progress
  one user's key cannot replay another user's stored response
  a key-required endpoint with Redis down fails closed

Limits
  oversized body → 413; wrong content type → 415; unknown JSON field → validation_failed

Concurrency
  stale version → version_conflict

Versioning
  a /api/v1 client is unaffected by any additive change
  regenerated docs/swagger.json and ts-sdk match the committed copies (CI check, §9)

Cross-cutting
  Profile field permissions differ correctly from admin-managed User field permissions (§10.9)
  meta.allowed_actions never contains an action the caller would be denied
```
